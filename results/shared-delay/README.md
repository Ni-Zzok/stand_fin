## Методика

Сохранены сценарии статьи: A — 20 последовательных запросов без конфликтов; B — 20 параллельных запросов, 14 на одну комнату и один интервал плюс 6 на другие интервалы. Каждый из двух режимов повторён пять раз при каждой задержке 0, 10 и 30 мс. Порядок режимов чередовался; выделенного прогрева нет. Всего 60 серий и 1200 HTTP-запросов бронирования.

Задержка моделирует ожидание ввода-вывода перед каждым вторичным действием: отдельно аудитом и отдельно уведомлением. При 10 мс на действие это 20 мс ожидания на успешное бронирование. Для обоих режимов вызывается одна функция с одинаковым значением; конфликтные запросы вторичных действий не выполняют. Дополнительная задержка только обработчика (`worker_delay_ms`) во всей матрице равна нулю. Значения факторов выбраны до измерений; они не являются замерами реального сервиса.

Среда: Windows 11, Python 3.12.14, PostgreSQL 18.3 x86_64-windows, Intel Core i7-11800H (8 ядер / 16 потоков). Клиент, один процесс API и отдельная БД на одной машине, HTTP localhost:18000, БД localhost:55432. Один фоновый обработчик; PostgreSQL с настройками по умолчанию (100 соединений, shared_buffers 128 MB). Остальные процессы не изолировались. Снимок установленных зависимостей сохранён в environment.txt.

## Интерпретация

При нулевой искусственной задержке в A гибридный режим медленнее; в B разница средних невелика. По этим данным нельзя заявлять универсальный выигрыш. При задержках 10 и 30 мс на действие перенос ожидания за границу ответа заметно снижает время ответа в обоих сценариях.

При этом быстрые ответы не означают быстрое завершение всей работы. В B при 30 мс среднее время ответа hybrid составляет около 64,8 мс против 138,1 мс у sync, но завершение всей серии — около 500,7 мс против 243,9 мс. Один обработчик последовательно выполняет фоновые задания, тогда как синхронные запросы к разным комнатам могут выполнять вторичные действия параллельно. Очередь накапливает отложенную работу.

В A при тех же 30 мс среднее ответа hybrid составляет около 5,1 мс против 68,5 мс у sync; завершение серии занимает примерно 1,31 и 1,37 секунды соответственно. Основное преимущество здесь — время ожидания пользователя, а объём вторичной работы сохраняется.

Синхронный режим удерживает блокировку комнаты до завершения вторичных действий и commit. Гибридный освобождает её после фиксации бронирования. В B эта разница влияет и на ответы о конфликтах; эффект нельзя приписывать исключительно скорости успешных ответов.

Вывод ограничен моделью ожидающего ввода-вывода, локальной средой и небольшим числом повторов. Статистическая значимость не оценивалась. Эксперимент не доказывает надёжность очереди, реальную стоимость уведомления или преимущество по полной длительности обработки. Числа с симуляцией не выдаются за результаты конференционного измерения.

## Как воспроизвести

Из корня проекта при работающем API выполните для каждого сценария a/b и задержки 0/10/30:

```sh
python load/compare_modes.py --scenario a --repeats 5 --secondary-delay-ms 10 --output results/local/scenario_a_delay10.csv
```

Для сверки на сохранённой среде использовался `--base-url http://127.0.0.1:18000`. Каждый запуск автоматически делает reset/seed, использует полученные ID, включает обработчик, задаёт обе задержки и дожидается фоновых действий между сериями. Сохранены все CSV и соседние JSON с телами запросов, ответами, внутренними метриками и параметрами запуска.

## Проверки
