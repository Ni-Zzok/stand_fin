# Booking Processing Lab

Исследовательский backend-стенд для сравнения синхронной и гибридной обработки бронирования помещений малого предприятия креативной индустрии. Предметный пример — музыкальная студия с общими помещениями и пересекающимися заявками.

Проект связан с работой А. С. Костина «Гибридная обработка операции бронирования в системе управления ресурсами малого предприятия креативной индустрии» (конференционные материалы, 2026). Сценарии сверены со статьёй и презентацией. [Связь с исследованием](docs/research-context.md) объясняет различия между опубликованными числами и новыми измерениями.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2, PostgreSQL, psycopg, asyncio.Queue, HTTPX. Это небольшой эксперимент с двумя режимами одной операции и общей БД.

| Режим | Что завершено перед ответом |
|---|---|
| `centralized_sync` | Проверка комнаты и пользователя, проверка пересечений, бронирование, аудит и запись уведомления в одной транзакции |
| `hybrid_async` | Проверки и бронирование подтверждены транзакцией; два вторичных задания переданы в очередь процесса |

Уведомление здесь означает запись в таблице, отправки почты нет. Синхронный SQLAlchemy выполняется в пуле потоков, чтобы не блокировать цикл событий API и обработчика очереди. Проверка конфликта и вставка защищены блокировкой строки комнаты `SELECT FOR UPDATE` до commit. Это сериализует заявки к одной комнате, включая непересекающиеся интервалы. Граница интервала — `[start_time, end_time)`: соседние интервалы разрешены.

## Быстрый запуск через Docker

Нужен работающий Docker Compose. Из корня репозитория:

```sh
docker compose up --build -d
```

API: http://127.0.0.1:8000, интерактивные примеры: http://127.0.0.1:8000/docs. Таблицы создаются при старте. Используются отдельная БД `booking_lab` и именованный том. Учётные данные в примере предназначены для локального стенда, порты открыты только на localhost.

```sh
docker compose exec app python scripts/seed_data.py
docker compose exec app python load/compare_modes.py --scenario a --repeats 5 --output results/local/scenario_a.csv
docker compose exec app python load/compare_modes.py --scenario b --repeats 5 --output results/local/scenario_b.csv
docker compose cp app:/app/results/local ./experiment-results
```

Скрипты очищают данные стенда перед каждым режимом. Используйте отдельную экспериментальную БД. Остановка с сохранением БД:

```sh
docker compose down
```

Файл Compose проверен на корректность конфигурации. Проверки и измерения в этом изменении выполнены с локальным PostgreSQL 18 и Python 3.12 на Windows; сборка контейнера в этой среде не запускалась.

## Сценарии и подготовка

- **A:** 20 последовательных запросов с непересекающимися интервалами. Ожидается 20 успешных операций, 0 конфликтов.
- **B:** 20 параллельных запросов. Первые 14 используют одну комнату и один интервал, остальные 6 — другие интервалы. Ожидается 7 успешных операций, 13 конфликтов.

Каждый режим начинает с reset и seed. ID комнат и пользователей берутся из ответа seed: последовательности PostgreSQL намеренно не сбрасываются. Повторный seed на непустых справочниках возвращает 409. Ошибка подготовки останавливает эксперимент до запросов бронирования.

Порядок режимов чередуется между повторами. После серии скрипт вызывает drain и проверяет числа ответов и завершённых фоновых заданий. Успех ответа гибридного режима сам по себе ещё не означает успешного аудита и уведомления. Скрипт сохраняет CSV и соседний `.csv.json` с ответами, метриками, версией Python, платформой, Git revision и хешами исходников. Несовпадение ожидаемых количеств даёт ненулевой код завершения. Отдельного прогрева нет; первый прогон включён в результаты.

## Одинаковая стоимость вторичных действий

`SECONDARY_DELAY_MS` задаёт имитацию ожидания ввода-вывода перед **каждым** из двух действий: аудитом и уведомлением. Она применяется одним и тем же кодом в обоих режимах. При 10 мс на действие одно успешное бронирование получает 20 мс моделируемого ожидания. Конфликтные заявки вторичных действий не выполняют. По умолчанию задержка равна нулю.

```sh
python load/compare_modes.py --scenario a --repeats 5 --secondary-delay-ms 10 --output results/local/a_delay10.csv
python load/compare_modes.py --scenario b --repeats 5 --secondary-delay-ms 10 --output results/local/b_delay10.csv
```

Настройка через API: `POST /experiments/secondary/delay` с `{"delay_ms": 10}`. Смена настройки дожидается завершения активных запросов и очереди; значение также сохраняется в каждом задании. Задержка выполняется в потоке вместе со вторичным действием и не блокирует цикл событий.

Это управляемая симуляция стоимости вторичных действий, которой не было в конференционном эксперименте. Цель, операция и сценарии A/B сохранены. Значения 0, 10 и 30 мс выбраны заранее для проверки зависимости от стоимости действий; они не получены из измерений реальной музыкальной студии. У синхронного режима ожидание входит в транзакцию и продлевает блокировку комнаты; у гибридного выполняется после commit бронирования. Эта разница является частью сравниваемых режимов.

[Результаты матрицы задержек](results/shared-delay/README.md) содержат все прогоны, включая нулевую задержку. [Предыдущие измерения](results/verified/README.md) сохранены как отдельный этап проверки до добавления общей симуляции.

## Метрики

| Поле CSV | Значение |
|---|---|
| `success_count`, `conflict_count`, `error_count` | Ответы 2xx, 409 и все прочие исходы, включая сетевые ошибки |
| `avg_response_ms`, `max_response_ms` | Клиентское время HTTP-запроса по монотонным часам; все ответы серии, включая конфликты |
| `request_batch_ms` | Время от начала серии до получения всех ответов |
| `completion_ms` | Время от начала серии до успешного ответа drain; включает дополнительный HTTP-запрос и ожидание очереди |
| `worker_completed`, `worker_failed` | Число успешно/неуспешно обработанных вторичных заданий после последнего reset |
| `avg_success_response_ms`, `avg_conflict_response_ms` | Среднее время успешных и конфликтных ответов по отдельности |
| `secondary_delay_ms`, `worker_delay_ms` | Общая задержка каждого вторичного действия и дополнительная задержка только фонового обработчика |
| `scenario`, `repetition` | Сценарий и номер повтора |

`GET /experiments/metrics` возвращает внутренние события. Для основного пути `duration_ms` измеряется до записи метрики и commit и **не равен HTTP latency**. События пишутся для успехов, конфликтов и неожиданных ошибок, когда БД доступна; ошибки входных данных 400/404/422 учитывает клиентский скрипт. Для фоновых событий длительность отсчитывается от постановки в очередь до подготовки метрики и включает ожидание и искусственную задержку, но не завершающий commit. Drain заканчивается после commit всех обработанных заданий, включая завершившиеся ошибкой. Смотрите также `failed`.

Параметр `WORKER_DELAY_MS` и API задержки воздействуют только на фоновый обработчик. Такой прогон демонстрирует накопление очереди и задержку завершения; он не является сравнением одинаково замедленных вторичных операций двух режимов:

```sh
python load/compare_modes.py --scenario b --repeats 1 --worker-delay-ms 25 --output results/local/scenario_b_delay25.csv
```

## API и границы эксперимента

- `POST /experiments/reset` — запрещает новые бронирования, дожидается активных запросов и фоновых заданий, очищает таблицы. При выключенном обработчике с заданиями или тайм-ауте возвращает 409 и не очищает таблицы. Счётчики фоновой обработки сбрасываются после успешной очистки.
- `POST /experiments/seed` — создаёт три комнаты и трёх пользователей, возвращает их ID.
- `POST /experiments/drain?timeout=30` — временно закрывает вход для новых бронирований и ждёт завершения очереди, возвращает счётчики. Допустимый timeout: до 300 секунд.
- `GET /experiments/worker`, `POST /experiments/worker/on`, `POST /experiments/worker/off`, `POST /experiments/worker/delay` с `{"delay_ms": 25}` — управление и состояние. `pending` включает задание, уже взятое обработчиком.
- `GET /rooms`, `GET /bookings`, `POST /bookings`, `GET /experiments/metrics` — данные и операция бронирования.

Для бронирования возьмите `room_id` и `user_id` из seed, передайте `start_time`, `end_time` в ISO 8601 без часового пояса и `mode`. Все интервалы в эксперименте трактуются в одной согласованной временной системе, преобразования часовых поясов нет. Пример тела доступен в `/docs`.

Запускайте **один процесс API и один эксперимент за раз**, без `--reload` во время измерений. Очередь, её счётчики и барьер reset находятся в памяти процесса. Блокировка PostgreSQL защищает бронирования между транзакциями, использующими этот путь записи, но управление экспериментом не рассчитано на несколько процессов или прямые записи в БД. Административные ручки не имеют авторизации и предназначены для локального стенда.

Очередь не хранится на диске, не повторяет упавшие задания и не гарантирует доставку при сбое. Между commit бронирования и постановкой заданий остаётся окно потери при аварии процесса. При штатном завершении приложение пытается обработать очередь в течение 30 секунд; принудительное завершение может потерять задания. Уведомления и аудит в гибридном режиме не входят в транзакцию бронирования.

Малая выборка, локальный запуск и общие ресурсы API/БД ограничивают выводы о производительности. Не заявляем преимущество режима по всем нагрузкам, промышленную надёжность или статистическую значимость. [Актуальные измерения и ограничения](results/shared-delay/README.md).

## Проверки

Используйте отдельную одноразовую PostgreSQL-базу. Тесты очищают её таблицы. Без `TEST_DATABASE_URL` интеграционные тесты пропускаются.

```sh
python -m pip install -r requirements-dev.txt
```

PowerShell:

```powershell
$env:TEST_DATABASE_URL='postgresql+psycopg://booking:booking@127.0.0.1:55433/booking_test'
python -m pytest -q
```

Bash:

```sh
TEST_DATABASE_URL='postgresql+psycopg://booking:booking@127.0.0.1:55433/booking_test' python -m pytest -q
```

Предварительно создайте `booking_test` с владельцем `booking`. Проверяются повторные reset/seed обоих режимов, соседние интервалы, 20 конкурирующих транзакций, доступность цикла событий при занятом потоке БД, ошибки подготовки/валидации/фиксации, задержанный и выключенный обработчик, ошибки вторичных действий, одинаковое применение задержки 0/10/30 мс в обоих режимах и смена настройки при ожидающих заданиях.

## Происхождение проекта

Репозиторий `stand_fin` содержит подготовленную версию на основе `stand_2`. [Первый прототип](https://github.com/Ni-Zzok/stand) использовал SQLite и отдельные классы репозиториев, общий принцип двух режимов и управление жизненным циклом обработчика. Здесь сохранена более компактная структура второго стенда и PostgreSQL; полезная идея явного управления обработчиком перенесена в FastAPI lifespan. Обе версии изначально содержали синхронный SQLAlchemy и очередь в памяти. Подробности: [контекст исследования](docs/research-context.md).

Название проекта — **Booking Processing Lab**, текущий репозиторий — `stand_fin`. Предыдущие репозитории сохраняются отдельно. Ссылка в резюме в рамках этой работы не изменялась.
