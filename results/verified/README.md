## Основные сценарии

Пять повторов каждого режима в каждом сценарии, по 20 запросов на повтор. Порядок режимов чередуется. Первый прогон включён, выделенного прогрева нет. Задержка обработчика — 0 мс.

| Сценарий | Режим | Успехи / конфликты / ошибки в каждом повторе | Среднее времени ответа по 5 повторам, мс | Диапазон средних, мс | Наибольший ответ, мс |
|---|---|---|---:|---:|---:|
| A | centralized_sync | 20 / 0 / 0 | 6,053 | 5,698–7,107 | 16,620 |
| A | hybrid_async | 20 / 0 / 0 | 6,511 | 5,929–7,302 | 30,612 |
| B | centralized_sync | 7 / 13 / 0 | 75,306 | 72,170–77,418 | 169,380 |
| B | hybrid_async | 7 / 13 / 0 | 74,320 | 69,992–76,416 | 175,132 |

Среднее в таблице — среднее пяти средних, каждый повтор содержит одинаковое число запросов. Для B оно включает ответы 409. Все серии достигли ожидаемых количеств. После drain в гибридном режиме выполнено 40 заданий в каждом повторе A и 14 в каждом повторе B, ошибок обработчика нет. В синхронном режиме фоновых заданий нет.

В A гибридный режим медленнее в среднем примерно на 7,6%. В B среднее меньше примерно на 1,3%, при этом наибольшая наблюдавшаяся задержка у него выше. Отдельные пары повторов дают разные направления различий. На этой малой локальной выборке устойчивое преимущество гибридного режима не установлено. Статистическая значимость не оценивалась. Вывод об ускорении из конференционных материалов этим запуском не воспроизведён.

## Проверка завершения фоновых действий

В `scenario_b_delay25.csv` сохранён отдельный диагностический прогон с задержкой 25 мс **на каждое фоновое задание**. Искусственная задержка не применяется к синхронному режиму, поэтому эта серия не используется как доказательство сравнительной производительности.

Для hybrid_async все ответы получены через 174,912 мс от начала серии, ответ drain — через 466,937 мс. Выполнены все 14 вторичных заданий без ошибок. Это демонстрирует, почему получение ответа и окончание вторичных действий нужно измерять отдельно. `completion_ms` включает время дополнительного HTTP-запроса drain.

## Воспроизведение

Из корня проекта при работающем API:

```sh
python load/compare_modes.py --base-url http://127.0.0.1:8000 --scenario a --repeats 5 --output results/local/scenario_a.csv
python load/compare_modes.py --base-url http://127.0.0.1:8000 --scenario b --repeats 5 --output results/local/scenario_b.csv
python load/compare_modes.py --base-url http://127.0.0.1:8000 --scenario b --repeats 1 --worker-delay-ms 25 --output results/local/scenario_b_delay25.csv
```

Сохранённые здесь измерения использовали порт API 18000 и PostgreSQL 55432 для изоляции от пользовательских сервисов. Копировать эти порты для сравнения не обязательно. Точное совпадение миллисекунд между машинами и запусками не ожидается. Данные конференционной таблицы и ограничения сопоставимости описаны в [контексте исследования](../../docs/research-context.md).

## Проверки исправлений

`python -m pytest -q`: 8 тестов пройдено на отдельной PostgreSQL-базе. Покрыты повторные reset/seed в обоих режимах, 20 конкурирующих независимых транзакций (1 успех, 19 конфликтов), соседние интервалы, отказы подготовки и валидации, откат при сбое до commit, работа API при занятом потоке БД, reset при выключенном/задержанном обработчике и явный учёт ошибки уведомления.

Один warning относится к устаревающему псевдониму AnyIO в зависимости Starlette/TestClient. Docker Compose прошёл проверку конфигурации; контейнерная сборка и измерения в контейнере не выполнялись.
